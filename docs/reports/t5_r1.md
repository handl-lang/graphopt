# T5 "lift any model" probe — round 1 (plateau test: second real model)

Follow-up to `whisper_experiment_r2.md` + `verify_lowmem.md`.  Same
pipeline, a *different* real HF model: **`google-t5/t5-small`**
(60.5 M params, encoder–decoder, relative-position-bias attention,
gated-GELU MLP — none of whisper's conv frontend / sinusoidal
positions).  Question: does a second unrelated real model go through
lift → census → optimize → lower → verify → deliver?

Hardware/software identical to the whisper rounds: RTX 2050 4 GB
(3.8 GiB free at start), torch 2.14.0+cu130, transformers 5.23.0.
Feeds: `input_ids` int64 `(1,128)` uniform `[0,32100)` +
`attention_mask` + precomputed `encoder_hidden_states` for the
decoder arm.  Forward-only timings, warmup 5 / reps 30.

Probe: `bench/drivers/probes/t5_probe.py` — `bench|opt <which>
[dtype] [max_enodes] [cpuparams]` plus `corpus_encoder()` /
`corpus_decoder()` callables for `model_corpus --module`.

## Baselines

| arm | fp32 | bf16 |
|---|---|---|
| encoder eager | 4.94 ms | 2.14 ms |
| encoder `torch.compile` | 4.28 ms | 1.22 ms |
| decoder step eager (seq=128) | 7.52 ms | 4.52 ms |
| decoder step `torch.compile` | 6.56 ms | 1.70 ms |

## Pipeline results

### encoder fp32 — full verified pass

- `opt.search`: **4.8 s** (whisper-base encoder: 4.2 s — same scale).
- `lower(verify=True)`: **0.3 s, verified=True**.
- delivered **4.34 ms** vs eager 4.94 (**1.14×**) and vs compile
  4.28 (**0.99× — parity with Inductor**).
- `CudaGraphRunner`: `cuda_graph=False, fail=kernel` — same refusal
  whisper encoders showed on this card.

### decoder fp32 — verified pass, and wall #3 did NOT repeat

- `opt.search`: **6.5 s** — whisper-base's decoder was killed at
  >10 min (r1) and >10 min again (r2, wall #3 open).  The T5 decoder
  saturates in seconds: the explosion is **whisper-decoder-specific**
  (scale/cache structure), not a property of "decoders".
- `lower(verify=True)`: 0.3 s, **verified=True**.
- delivered **7.49 ms** vs eager 7.52 (**1.004×**) and vs compile
  6.56 (**0.88× — slower than Inductor**).

### encoder bf16 — verified pass (contrast: whisper bf16 verified=False)

- `opt.search`: 5.1 s; `lower+verify` 0.1 s, **verified=True**;
  delivered **1.90 ms** vs eager 2.14 (**1.13×**) and vs compile
  1.22 (**0.64×**).  The bf16 pointwise tolerance wall that rejected
  whisper-small/turbo bf16 (`verify_lowmem.md`) does **not** fire
  here — T5's rewrite set apparently stays inside `rtol=1e-4`.
- Caveat below (dtype keying) applies to how "bf16" was fed.

## Walls hit — in order

### Wall 1 — all-integer feeds never trigger `_align_to`

First `opt encoder fp32` run: search fine (5.4 s), then
`lower+verify` failed in 0.2 s —
`RuntimeError: Expected all tensors to be on the same device …
index_select`, and the unverified delivery failed the same way.

Diagnosis: T5's lifted encoder takes **only integer inputs**
(`input_ids`, `attention_mask` as int64).  `IRModule._align_to`
(torch_bridge.py:3542) keys its one-shot device/dtype alignment off
`_sibling_like(xs)` — the first *floating-point* input tensor.  With
no float input it is a silent no-op, so the CPU-baked `fused_*`
weight-chain tensors (`_fold_weight_chains` materialises
position-bias `(128,128)` masks etc. on CPU at construction) collide
with the CUDA params at first eval.  Whisper never hit this because
its encoder feed is a float log-mel tensor.

**Probe workaround**: `attention_mask` as float32 — numerically
identical for an all-ones mask (verified max diff 0.0 vs long), and
it engages `_align_to`.  This is a real generalisation gap: any
lifted submodule whose inputs are all int/bool (pure token pipelines)
will hit it on a non-CPU device.

### Wall 2 — `torch.min(a, b)` exports to the *reduction* binding (silent wrong-answer)

With wall 1 worked around, `lower+verify` hit a CUDA **device-side
assert** (`vectorized_gather … index out of bounds`) inside
`verify_module`; on CPU the same term raises `IndexError: index out
of range in self` in `torch.embedding`.

Root cause, isolated by evaluating the exported IR term directly:

- T5's `relative_position_bucket` ends with
  `torch.min(rel_if_large, torch.full_like(...))` — the *elementwise*
  two-operand spelling (`aten.minimum`).
- The exporter names IR ops off the Python callable's `__name__`;
  `torch.min`'s is `"min"`, so the term mints op **`min`** — which
  in the op tables is the *whole-tensor reduction*
  (`torch_bridge.py:1655`: `"min": lambda x,*a,**kw: torch.min(x)`
  when no `dim`).  The second operand is dropped and the scalar
  reduction broadcasts.
- Measured on the exported term: the bucket-index subtree evaluates
  to `int64` with `min = -9223372036854775800` (INT64_MIN — the
  `log(0) → -inf → to(int64)` lane surviving through the broken
  `min`), where the eager bucket is `[0, 32)`.  The corrupted index
  feeds `relative_attention_bias`'s `embedding` gather → OOB.

This is worse than a refusal: **the pipeline produces a wrong
answer**, and on CUDA it surfaces as a sticky device-side assert
that poisons the context (the probe process died; a fresh process
was needed).  `torch.max(a, b)` presumably has the symmetric bug
(`"max"` → reduction binding) — not separately exercised.

**Probe workaround** (`_patch_min_max` in the probe, applied in
`load()`): re-dispatch two-operand `torch.min`/`torch.max` to
`torch.minimum`/`torch.maximum` — semantically identical — so the
exporter sees `aten.minimum` → IR op `minimum` → the correct
`torch.minimum` binding (torch_bridge.py:2163).  Single-operand
reduction spellings pass through.  This unblocked the encoder AND
the decoder arms above; it is a probe-local patch, **not a fix** —
the exporter/binding collision wants a real repair upstream
(distinguish `aten.minimum`/`aten.maximum` from `aten.min`/`aten.max`
at export, or make the `min`/`max` bindings arity-aware).

### Wall 3 — dtype keying silently upcasts bf16 deliveries

`_align_to` moves floating params to `(like.device, like.dtype)`
where `like` is the first float *input*.  T5's only float input is
the mask; an fp32 mask against bf16 weights casts **every delivered
weight to fp32**.  Measured: bf16 model + fp32 mask → delivered
4.62 ms (≈ the fp32 delivery's 4.34 ms), `verified=False`;
bf16 model + bf16 mask → delivered 1.90 ms, `verified=True`.
Whisper never noticed because its whole feed shares the model dtype.
For int-heavy models the "input dtype" is whatever float tensor the
caller happened to pass — a footgun worth documenting.

### Wall 4 — `model_corpus` intake dies in `_seq_scan_sites` (host RAM, not VRAM)

`python -m mlopt_discovery.model_corpus --module
bench.drivers.probes.t5_probe:corpus_encoder --mutants 4 --corpus
bench --reps 3 --gen-reps 3 --dtype fp32` was run twice; **both
killed by earlyoom** (VmRSS 7.2 GB and 5.1 GB, SIGTERM at the 10 %
mem floor — same daemon `verify_lowmem.md` flagged).  A
`--mutants 0 --no-probe` census-only run also died at 7.7 GB, so the
probe/mutant stages are not the cause.

Stage isolation (diagnostic runs with a 3.5–4.2 GB watchdog,
`/tmp/t5_diag*.py` — not committed):

| stage | result |
|---|---|
| `corpus_encoder()` + `export_ir(fp32)` | 0.5 s, 51 leaves, RSS 0.95 GB |
| `_probe_knobs` | instant — `term_expansion=292172` → `large_term`, auto bounds: `spec_cap=512`, `key_cap=20000`, `max_claims=16`, `claim_budget=2.0` |
| `coverage_report` (bench corpus, 66 terms) | 0.5 s — model: 69 op-tuples / 121 shapes; **58 novel op-tuples, 121 novel shapes**; 181 subterms honestly skipped by the 10 K shape-key cap |
| `play._mint_tiers` → `gen` tier | 0.0 s, 57 sites → 11 handlers |
| `play._mint_tiers` → **`scan` tier** | **`_scan_sites` 0.0 s (0 sites); `_seq_scan_sites` >3.5 GB RSS, never returned** |

So the coverage verdict itself is cheap and clean — the wall is the
scan-tier site collector `play._seq_scan_sites`
(play.py:2204), which `_all_scan_sites` calls *uncapped* (the
`spec_cap` bound only reaches the `gen`/`reduction` collectors —
`_mint_tiers`, play.py:2566-2570).  The collector enumerates raw
recurrence candidates via `_seq_spines` per node and then verifies
each with `_seq_site`/`_seq_traj_states` walks over the whole term;
the T5 encoder term's tree-expansion is 292 K (vs whisper-base's
119 K), and the candidate/traj machinery is not DAG-bounded — the
same disease `model_corpus_scaling.md` fixed in the *other*
collectors, still live here.  It emits at most `_SEQ_SITE_CAP=16`
sites but the cap bounds output, not the enumeration.

Consequence: **the coverage half of the corpus pipeline works on a
second real model; the measured-referee half cannot intake it.**
`gen_probe`/mutants never ran.  `corpus_decoder` was not attempted —
it would hit the same uncapped collector (and likely wall 2's
decoder structure) before any measurement.

| stage | whisper-small fp32 | t5-small fp32 |
|---|---|---|
| export/lift | pass | pass (after float-mask workaround) |
| search | 27–29 s | **4.8 s** |
| lower+verify | verified | **verified** |

## Verdict for "any model" (t5 r1)

- The core deliver path **generalises**: a second unrelated real
  encoder–decoder model lifts, searches, lowers, verifies and
  delivers on 4 GB with a measured ~1.1× vs eager.  Two new walls
  were found and are *characterised*, not fixed: int-only feeds skip
  `_align_to`, and two-operand `torch.min`/`torch.max` mint
  reduction-bound ops (silent wrong answer → OOB gather).
- The corpus/referee path does **not** yet generalise: coverage is
  cheap and reports 58 novel op-tuples / 121 novel shapes for T5,
  but `_seq_scan_sites`'s unbounded enumeration OOMs host RAM before
  any claim is priced.  That is the next wall to fix for "any
  model" — it is a collector bound, not a measurement failure.
