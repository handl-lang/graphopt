# Delivery — a rule pays as a kernel, not as a step

**Method.** The same machine-minted `synop*` folds, measured twice: as one more step inside a real module (`pay_measured.json`, `marginal = delivered/spelled`) and as an isolated compiled body over 1 M elements (`prim_kernel*.json`, `kernel/binding`). Paired on the op name.

- ops seen: 12 · paired in both forms: 3 · loss tolerance: >1.02x

## Findings

### NEGATIVE — Delivered as one more step inside a module, the minted folds lose.

3/3 paired ops lose as a step (worst 2.66x slower)

### WIN — Delivered as an isolated kernel body, the same ops win.

3/3 win as a kernel — median 2.72x over the binding

### WIN — The sign of the result is set by the delivery, not by the law: the same op flips from loss to win.

3/3 paired ops flip — delivery is the variable

## What this establishes, and what it does not

- It establishes that **delivery** changes the sign for these ops. It does not establish that every losing zoo row flips: these ops are the ones the primitive mint produced, and the zoo rows carry different shapes and dtypes.
- The paired set is small and drawn from the scan/gated-LRU family. The P1 gate (the 46 losing zoo rows) is the test that generalises it, and it is not answered here.
- `kernel_over_binding` is measured at 1 M elements with the fp64 verify contract; a module-scale delivery also pays materialization and layout, which this ratio excludes.
