A tensor program is operations over data. Read it as a tree: the leaves are inputs and weights, every node is an operation, and work flows upward to one root. That root is the answer.

Nothing about optimization makes sense until this is concrete, so start here: pick a program and read every node's shape and its share of the work.

total flops

Here is the observation the whole system rests on: two different trees can compute exactly the same function. Matrix multiplication is associative, so these two agree on every input — but they form different-sized intermediates, so they do different amounts of work.

Before you look: with those dimensions, guess which tree is cheaper.

Careful with the claim. Reassociating a matrix chain is a classic compiler optimization (Sethi–Ullman, 1975), so "no compiler can do this" would be false. The honest statement is narrower: a rewriter that cannot reassociate is stuck with the tree it was handed.

The system is measured on real programs, not hand-written terms. The intake takes a candidate nn.Module through torch.export → export_to_ir → classify → persist, and every candidate lands in exactly one class: ingested (bound, lowered, verified fp64), census-only (an op is unbound), or rejected (torch.export raised).

The intake's real yield is the defect list. Three real modules exported and bound cleanly but lowered wrong — each a boundary that emitted a term that was never the program (nn.MultiheadAttention, nn.TransformerDecoderLayer, nn.LSTM). Lowering the ingested term and diffing fp64 against the original found all three; the corpus is now 166 workloads, 114 verified, with the defects pinned as a regression test. (project/retros/workload-intake.md, intake-defect-fixes.md.)

If two trees can be equal, how many equal trees are there? The answer is not a number — it is the closure of your laws. Start from a program and apply laws until nothing new appears; everything you reach is equivalent. The structure that computes that closure is the e-graph — it holds every equivalent form at once.

Flip between a rewriter with no laws and one with six. Same programs, same search effort — a different language.

With no laws the rewriter never leaves the starting program, so the cheaper tree is unreachable — tuning the schedule of the tree you were handed cannot find a different tree.

So where do laws come from? Not from operations. They are consequences of the algebraic structure a program instantiates. A monoid gives you associativity. A comonoid gives you duplication. Pick a structure and see the laws — and the transformation — it licenses.

This is why catopt finds things op-level compilers cannot: the law lives in the structure, not in any op's name.
In the real system, laws are found, not only written. The shipped law bank is a hand-written kernel plus 11 laws the machine discovered — the newest, mul_unsq_nat, is a two-sided unsqueeze naturality worth −12.3 % on its source workload, and four more (select_mul — mul(select u, select v) → select (mul u v), 25 corpus sites — softmax_fold, silu_fold and glu_fold) were machine-assisted but hand-integrated. The corpus is machine-fed too: 166 real nn.* workloads through the export boundary, 114 verified — an intake that also caught three lowering bugs no test caught. Later levels follow that machinery end to end; here, note only its shape: structure proposes, and a numeric check decides.

Rewriting freely is dangerous — you could rewrite into something that computes the wrong answer. So every move carries a derivation, and the derivation is re-checked on real numbers. Apply moves, then replay the certificate.

cost
This is the safety argument. The referee runs after the search, not inside it — which is why a heuristic player can pick a terrible move but never an unsound one.
The referee judges machines too — and gets audited. A machine-discovered candidate that fired 23 times and lowered cost was rejected by the numeric oracle — a false equality. And when a machine proposer offered select(u) = unsqueeze(select(u)) as a "law", it exposed a hole in the oracle itself: the equality check broadcast across ranks, so a rank-changing rewrite scored "true". The fix — exact shape equality before the value comparison — flipped three past candidates true → false, and no ship verdict changed. The referee referees humans, machines, and itself.

Then the machine audited its own first law. A view/index oracle built to resolve the "unproven" bucket swept every real site plus synthesized edge cases — and proved the shipped select_mul unsound: broadcasting mul along the selected axis changes the result. All 13 real sites happened to satisfy the missing condition, so it never bit — until the machine went looking off the corpus. Constrained now, by a condition that is itself pure data. And the object language caught up: every shipped law is now fully serializable — pattern, condition, proof — and the machine can declare objects (fold / lift / compose a new one into the store) and have the whole checking round admit or refuse it. Two built objects already passed.

The class can be astronomically large — you cannot enumerate it. So you need a policy: a rule for what to try next. Watch three players spend six moves each, then take the model on yourself.

The subtlety: a rule is encoded by its shape, not its index. That is what lets the player score a rule it has never seen — which is the next level's point.
The honest ledger — what the player can and can't do yet.
  • Beats the best cheap baseline at scale. The shipped contraction player wins at n = 40 — 0.87–0.98× vs best-of-N randomized greedy at equal wall-clock — by three parts composed: teacher distillation (knowledge), lockstep batching (~15× more episodes), policy sampling (diversity). It still starves under ~50 ms budgets.
  • Loses to enumeration where structure is enumerable. A learned law-proposer yields ~10× fewer true candidates per oracle call than the pipeline's plain enumeration — the corpus's shapes, not the player's imagination, carry the discoveries.
  • Cannot feed itself. Resampling the corpus to train on freshly named atoms provably yields zero new op-tuples; mutation's novel tuples are semantically arbitrary. Self-play needs real programs — their shapes carry the justifications.

Drag the sliders: on a small program the launch term dominates; on a big one the roofline does. That switch — which term wins — is hardware, and it is why the same program can be optimal on one device and not another.
A model can be calibrated by measurement — and being wrong has consequences. The real pipeline's launch-count cost model once priced a batched-scan delivery ~20–30 % cheaper than the generic eval; on the GPU the same term measured 1.9–2.7× slower. The modeled executor-routing comparison was wrong on 5 of 6 cases. The fix feeds measured per-executor corrections — a TargetProfile — into the delivered-cost comparison: the corrected selection lands on the measured-fastest member on all 12 probe cases. And where prediction is not enough, the Autotuned strategy bypasses it: re-lower each candidate, time it on-device, ship the winner — it honestly ships the raw model when that measures fastest.

One model is not enough. The system prices a term with a family: static features describe, a roofline bounds, an executor adds the launch cost of the route it would take, and delivered pricing bills the term under the lowering it would actually be delivered by. Every level so far treated the law library as a flat set. It is not — laws relate. One can derive another (then it adds no new reach). Two can be the same equality carried in two directions (an inverse pair). And two laws that fire on the same redex can commute — or diverge.

A relation between laws is one level up from a law, and you measure it the way you measure everything else here: fire each law once on a shared redex, take the two one-step reducts, and ask whether the library rejoins them. Probe a pair:

In the real library this probe is a catalogue. All 83 shipped rules, pairwise: 59 axioms / 22 lemmas / 2 redundant — the axiom/lemma split is a recorded field on every rule, and the lemmas are equivalence classes of "the same law two ways". Exactly one coherence gap was measured: silu_expand × swiglu_fuse — expanding the silu inside the mul destroys the fuse redex. Everything so far assumed the vocabulary was given: five ops, six laws. The real system can grow its own vocabulary — mint a new semantic atom from a measured need. ADR 0007's four layers, in order: a need the runtime sees but no law names; a signature read off real occurrences; a handler proposed from a structured grammar and verified numerically; the laws the atom satisfies, synthesized and certified — then the admission gauntlet and a pay probe.

The op-graph IR is the lowering surface. A second, parallel presentation re-reads it as morphisms: seq (composition), par (the monoidal product ⊗), arr (apply an op), dup (Δ — sharing, made explicit), and loop (a typed trace). The bridge is a bijection: dagToComb fans shared subterms out into Δ sites; combToDag inlines them back.

Sharing as structure is the strongest immediate argument. When Δ is a morphism, fan-out is explicit — the DAG-vs-tree ambiguity class of bugs is impossible by construction. And loop makes recurrence first-class: the RetNet loop form the machine extracted is a spelled seq(pre, loop(step, K), post), verified against the real _ChunkedRetention at 1e-7–2.6e-7. The bridge is measured: 321/321 exported workloads round-trip structurally exact, zero ops refuse translation. (ADR 0008.)

Rewriting is exact by default: the certificate replays and the result is the same function. But sometimes a near-equal program is allowed — if it carries a certified bound on how far it may drift. That opens a second lane: offer members whose error is inside a budget ε. It is not free. Approximation must clear two gates — a certificate (is it within ε?) and an economics test (is it cheaper?).
